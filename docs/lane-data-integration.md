# 真实多路口车道接入说明

核查日期：2026-10-24。

目标流程：在本应用输入终点 → 选择实际路线 → 随车辆前进，持续显示这条路线前方 2～3 个物理路口的车道、推荐方向及沿路线距离。

## 当前实现及限制

- `Home.ets` / `HomeMap.ets`：原生地图首页；首次授权后启动自动定位，搜索目的地、标记终点并打开原生导航选路页。首页地图在后台或导航页面隐藏时暂停定位，返回恢复。默认 Key 由本机 `.local/` 在构建时注入被 Git 忽略的资源，不提交实际 Key。
- `LaneLookAheadSession.ets` / `LaneSdkData.ets` / `LanePreview.ets`（0.0.13）：SDK 选定路线的前方 2 / 3 个导航引导点、实时车道回调及本机历史参考。引导点不冒充完整物理路口列表。具体学习条件与限制见文末。
- `PlanRoute.ets`：高德地点搜索、终点选择、当前位置导航入口，以及可选的指定起点 Web 规划与分段预览。
- `NativeNavigation.ets`：高德 HarmonyOS NEXT 导航 SDK 11.2.1 的原生地图选路及 GPS 导航。先完成隐私说明与精确位置授权，再由 SDK 获取当前位置并导航；需要绑定当前签名 AppID 的鸿蒙 Key。
- `RoutePlanning.ets`：请求参数、地点及规划响应解析。高德地点与路线参数统一使用 GCJ-02。不会把原始 WGS-84 GPS 坐标直接传给它。
- `HttpRouteTransport.ets`：HTTPS、超时、取消请求和连接资源释放。
- `Guidance.ets`：已有按沿路线进度筛选前方物理路口的引擎，支持 2 / 3 个路口、独立车道推荐、缺失数据和路线不匹配保护。当前只有演示数据在使用它。

当前位置导航已交给原生导航 SDK 获取位置、匹配道路及显示转向，并启用内置语音。Web 路线分段预览仍是独立的规划预览，不会连接到物理路口引擎；真实路线也不会复用演示路口。真实多路口车道数据源尚未接入。当前仅验证前台导航，后台、锁屏和实车行驶仍待验证。

## 车道数据源需要满足的契约

要启用真实多路口提示，应先用一条实际路线证明可以在驶入第一个路口前同时取得以下信息：

1. 与用户选定路线一致的路线标识及版本；重规划、备选路线切换后必须更新。
2. 沿这条路线依次经过的物理路口标识，包括需要直行的路口；不能只列转弯机动点或只列红绿灯。
3. 每个路口到起点的沿路线累计距离，而不是 GPS 直线距离。
4. 每个路口由左到右的车道允许方向，以及该选定路线的推荐方向。混合车道的推荐分支不能全部高亮。
5. 哪些路口尚无车道数据，以及数据有效期或失效通知。
6. 当前路线的地图匹配进度，以及偏航、定位失效、重规划等事件。

满足契约后，由供应商适配层构造 `RouteSnapshot`、`Junction`、`LaneGuidance` 和 `RouteProgress`，交给 `LookAheadEngine.preview()`；禁止根据“下一步左转”猜测左转车道数量。

如果只有当前路口车道，应只显示该路口已确认的信息，后续路口标为暂无数据；若连物理路口列表也不完整，应明确显示覆盖不足，不能标为“前方没有路口”。每次切换路线，应先清空旧路线的路口、车道及进度，再等待新数据。

## 0.0.13 连续引导点与车道历史

核对 SDK 11.2.1 公开声明和官方 [导航信息回调](https://lbs.amap.com/api/harmonyosnext-navi-sdk/guide/navigation-map/navi-info)、[导航组件高级功能](https://lbs.amap.com/api/harmonyosnext-navi-sdk/guide/navi-component/advanced-functions)。`IAMapLaneInfo` 只有背景方向、推荐方向与车道数量，没有坐标、路口 ID、所属 step/link 或距离；不能直接取得整条路线未来车道。

因此新功能以实际 `getNaviPath().getSteps()` 为不完整引导点集合，使用 `mCurSegIndex` / `mSegRemainDis` 计算沿路线距离。通过 `setCustomAboveToBottomComponent` 加入原生导航页面，保留高德原有定位、选路和语音。它不把 Web 分段或演示路口用于实际导航。

只有单灯且信号所在末端 link 与 step 端点相同、当前点距车不超过 200 米时才关联实时车道。进一步接近至 80 米并连续通过该点后才保存。关联依然是推断：未收到多个不同车道回调不代表没有其他无灯路口，因此历史始终标作参考。复杂、多灯、方向不匹配的点保持未知，不追求以错误匹配增加覆盖率。

历史 key 包含进口/出口道路、转向图标和端点前后各四个方向有序坐标（GCJ-02 保留六位小数）。它不依赖会变化的路线 ID，不因路口同名而跨方向复用。完整 key 避免短哈希碰撞；严格匹配也会减少复用率，路线形状变化可能需要重新学习。

进度超过 15 秒未更新、信号弱、定位关闭、偏航或重算时撤下旧提示；车道回调须在最近 2.5 秒导航进度后收到，同段连续匹配的位置更新会保持当前可见车道有效，允许正常等红灯。中断更新后不再延长有效期。同段车道组冲突撤销待存观测并删除该点旧历史（包括隐藏后出现另一组）；隐藏车道、模拟、跳段及超过 5 秒不连续的越点均不提交。选路线映射键与原生 path ID 分别处理，不能确认属于所选路线的回调不参与预览或学习，监听与定时器在退出时清理。

记录仅存应用沙箱 `filesDir/lane-observations-v1.json`，临时文件写完后原子替换，读写失败不阻止导航；最多 500 条，读取上限 2 MB，7 天有效。设置提供清除入口。不记录完整轨迹、不上传，也不使用模拟数据填充真实缓存。

本版本 49 项逻辑测试通过，包含多个未来引导点读取历史、驶过后切换、历史过期、歧义撤销和红灯停等。ArkTS 编译及签名 HAP 安装通过；真机验证了实际导航页的新面板、弱卫星信号下暂停、数量切换、收起/展开、退出，以及连续两次清除历史文件（首次创建与覆盖）。尚未实车采集连续路口并重复行驶，真实历史覆盖和关联准确性仍待道路验证。

退出 GPS 导航时关闭整组 SDK 页面并回首页；再次进入创建新会话，退出后的旧回调不可重启。真机复查了「开始 → 退出回首页 → 再次进入」：新面板能重新读取所选路线，避免 SDK 选路页复用旧启动回调时停在等待状态。

## 0.0.15 采集诊断

导航面板增加采集状态、原因与历史写入次数；「设置 → 车道采集诊断」查看最近一次导航的车道回调数、有效车道回调数、通过路口确认数、写入成功次数，以及读取缓存后得到的本机有效历史条数。回调可能重复，写入包含历史更新或撤销，这些计数均不代表不同物理路口数量。

分别记录未收到车道、空数据、路口关联条件不足（多灯、信号灯不在末端、缺少进出几何等）、等待靠近、待通过确认、车道隐藏、车道组冲突、位置延迟、非连续越点、偏航重算、弱定位、模拟导航及文件写入失败。额外统计 SDK 的多组车道回调，此类回调暂不用于路口学习；诊断新增可见性，不放宽既有保存条件。

摘要存于应用私有目录 `filesDir/lane-collection-v1.json`，保留最近一次导航的计数、原因汇总和最多 60 条状态变化事件。连续相同原因合并；原因次数不是丢失的路口数。常规写入间隔至少 5 秒，历史写入成功或导航结束时强制保存；异常退出可能丢失最近约 5 秒诊断。摘要不包含 Key、道路名称、路线标识或坐标，不上传；历史文件与诊断文件分别原子替换，失败时保留旧文件并提示，诊断失败不阻断导航。

旧版本未记录上述诊断，无法追溯 0.0.14 的实车行驶为何没有留下历史；新版仍需真实行驶采集后再检查摘要和历史复用。

## 0.0.17 路线位置匹配修复

核对本机 SDK 11.2.1 声明、回调传值实现及真机诊断后，确认 `INaviInfo.pathID` 虽声明为 `number`，实际导航回调会传入 `bigint`。旧代码在选路映射未命中时使用 `Number.isSafeInteger()` 校验，导致有效原生路线 ID 被拒绝，后续车道回调缺少可用于关联的路线位置。

新增边界适配：安全整数、`bigint` 与规范十进制字符串分别校验，优先解析选路键，再用精确字符串比较原生 ID。拒绝已经丢失精度的数值、其他路线与无效标识，不通过转为浮点数近似比较来放宽条件。诊断仅记录标识类型、匹配方式和失败类别，不保存实际 ID；既有路口关联、连续通过和过期规则保持不变。

71 项宿主机逻辑测试与完整签名构建通过，新增回归覆盖大整数 ID、不同运行时类型、选路映射、相邻 ID、数值精度丢失与诊断脱敏。0.0.17 已覆盖安装到授权手机，真实 GPS 启动后诊断确认“路线位置已匹配（bigint，原生标识精确比较）”，随后静止弱定位暂停与退出正常。本次没有实际行驶或收到车道回调；连续路口保存和再次经过时的历史复用仍待实车验证。测试导航记录已删除，原有导航历史完整保留。
