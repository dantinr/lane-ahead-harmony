# 真实多路口车道接入说明

核查日期：2026-10-24。

目标流程：在本应用输入终点 → 选择实际路线 → 随车辆前进，持续显示这条路线前方 2～3 个物理路口的车道、推荐方向及沿路线距离。

## 当前实现及限制

- `PlanRoute.ets`：高德地点搜索、明确选择起终点、驾车备选路线、选择结果与分段预览。需要用户自己的 Web 服务 Key；已完成电脑端及手机端真实搜索与选路验证。
- `RoutePlanning.ets`：请求参数、地点及规划响应解析。高德地点与路线参数统一使用 GCJ-02。不会把原始 WGS-84 GPS 坐标直接传给它。
- `HttpRouteTransport.ets`：HTTPS、超时、取消请求和连接资源释放。
- `Guidance.ets`：已有按沿路线进度筛选前方物理路口的引擎，支持 2 / 3 个路口、独立车道推荐、缺失数据和路线不匹配保护。当前只有演示数据在使用它。

真实路线页面没有接入定位、地图匹配、导航语音或多路口车道源，不能用于实时驾驶导航。路线分段预览不会连接到物理路口引擎；真实路线也不会复用演示路口。

## 已核查的官方接口

| 接口 | 已确认的内容 | 对本需求的边界 |
| --- | --- | --- |
| [高德 Web 搜索 POI 2.0](https://lbs.amap.com/api/webservice/guide/api-advanced/newpoisearch) | 地点名称、地址及坐标；可限制城市 | 用于用户选择起终点 |
| [高德 Web 路径规划 2.0](https://lbs.amap.com/api/webservice/guide/api/newroute) | 多方案、路线距离、分段指令、分段距离及耗时等可选字段 | 文档未定义每个未来物理路口的车道列表；步骤不等于物理路口 |
| [高德鸿蒙导航实时数据](https://lbs.amap.com/api/harmonyosnext-navi-sdk/guide/navigation-map/navi-info) | `showLaneInfo` / `hideLaneInfo` 车道回调 | 未据此确认能预取后方第 2 / 3 个路口的车道 |
| [高德鸿蒙 API 参考](https://a.amap.com/lbs-dev-yuntu/static/reference/harmonyosnext-sdk/navi/index.html) | `IAMapLaneInfo` 的背景车道、推荐车道和数量；`AMapNaviPath.getSteps()`；`AMapNaviLink` 道路及交通灯字段 | 本次核查没有在公开 Path / Step / Link 模型中找到可按未来路口获取车道的接口。不能将这点扩大为“供应商完全没有该能力” |
| [百度鸿蒙导航实时数据](https://lbs.baidu.com/docs/harmony?title=harmonycarsdk/navigate/obtain) | `onLaneInfoChange` 按从左到右顺序返回车道图标；诱导面板有当前及后续道路字段 | 未确认未来多个物理路口的完整车道预取能力 |
| [OSRM API](https://project-osrm.org/docs/v5.24.0/api/) | 路线 step 中有 `intersections`；intersection 可包含 `lanes` | 可作为后续候选验证，但缺失车道字段代表没有数据；国内覆盖、坐标体系、服务部署及地图匹配均需实测。本次没有集成 |

因此，高德目前只作为地点搜索和规划服务接入，不将它标为“已经满足多路口车道需求”。没有通过模拟导航快进、录屏识别或抓取其他导航软件来伪造未来车道。

## 北京指定路线的初步核查

按用户提供的「望京地铁站 → 301 医院」测试，以公开 POI 附近坐标向 OSRM 公共演示服务请求驾车路线。望京通过地理范围筛选排除了同名铁路站；终点取复兴路院区。两端使用 WGS-84，取点不代表指定出入口，尚未实车核对。

2026-10-24 本次响应返回两个方案：约 25.3 km 和 25.8 km；两者带 `lanes` 数据的交叉点对象数量均为 **0**。这说明该服务本次响应不足以支持此路线的多路口车道提示，不能将结果扩大到所有国内路线，也不能把“缺少车道数据”说成“道路没有车道”。响应中的 88 / 92 个 intersection 对象是路网对象，不能直接当作物理路口数。

精简核查结果保存在 [北京路线车道数据核查](../artifacts/beijing-lane-feasibility.json)，包含可复现请求和坐标。另一次柏林路线请求返回了 9 处带车道数据的交叉点对象，说明 OSRM 协议具备提前返回沿路线车道数据的能力，但覆盖取决于具体路网数据。当前不将其集成或推荐为北京车道数据源。

## 车道数据源需要满足的契约

要启用真实多路口提示，应先用一条实际路线证明可以在驶入第一个路口前同时取得以下信息：

1. 与用户选定路线一致的路线标识及版本；重规划、备选路线切换后必须更新。
2. 沿这条路线依次经过的物理路口标识，包括需要直行的路口；不能只列转弯机动点或只列红绿灯。
3. 每个路口到起点的沿路线累计距离，而不是 GPS 直线距离。
4. 每个路口由左到右的车道允许方向，以及该选定路线的推荐方向。混合车道的推荐分支不能全部高亮。
5. 哪些路口尚无车道数据，以及数据有效期或失效通知。
6. 当前路线的地图匹配进度，以及偏航、定位失效、重规划等事件。

满足契约后，由供应商适配层构造 `RouteSnapshot`、`Junction`、`LaneGuidance` 和 `RouteProgress`，交给 `LookAheadEngine.preview()`；禁止根据“下一步左转”猜测左转车道数量。

如果只有当前路口车道，应只显示该路口已确认的信息，后续路口标为暂无数据；若连物理路口列表也不完整，应明确显示覆盖不足，不能标为“前方没有路口”。每次切换路线，应先清空旧路线的路口、车道及进度，再等待新数据。
